# Application architecture

The repository contains a production-line web/ application and an isolated pnpm rebuild workspace. The two APIs have separate routes and authentication cookies. An account defaults to sync generation 1. The incremental writer accepts only accounts explicitly assigned to generation 2 in the target database. Production cutover must first fence writes from legacy clients. Setting the generation alone cannot fence a separate Worker.

The Hono application in apps/api/src/app.ts consumes a repository and a password verifier. Node and Workers use the same handlers, rate limits and SQL transactions. The Worker adapter accepts a Hyperdrive binding. PostgreSQL owns account ordering and change history. The database migration runner verifies the ordered SHA-256 history while holding a transaction lock. Contracts publish a versioned water operation, validated requests, cursor responses and an OpenAPI sync description.

A per-account row lock serializes changes with their feed and receipt. The immutable change log contains operation ID, base revision, committed cursor and payload. SQL NULL represents a tombstone. Replaying an operation with the same contents returns its original result. Reusing an operation ID with different data, or writing against a stale revision, returns 409. Client-supplied account IDs never select the owner.

The combined Worker selects the Hono API for /api/v2 and routes the original service protocol to isolated native namespaces. The host-independent Hono services share the same contracts on Node and Workerd. The ordinary /medication/ entry serves the whole product, including the original CSS, dialogs, day navigation, icons, translations, offline storage and deep links. The build substitutes typed modules for routing, account transport and selected React feature views. The feature parity ledger lists those views. Other UI controllers still share the release implementation.

The primary pnpm frontend resolves its own esbuild and Workbox dependencies. `packages/web-build` contains the shared asset compiler called separately by the pnpm product and by the incumbent npm application. The pnpm build still consumes templates and client sources from `web/ui` and `web/public`. Fresh visits can render React onboarding after the IndexedDB read and before dashboard code downloads. The dashboard stays on the existing path for returning users and deep links. The shell scope, origin, and versioned asset manifest stay compatible with the installed app. See the [frontend migration ledger](FRONTEND_PORT.md).

The care API stores owner-scoped, revisioned documents. A bounded change contains field updates and stable row insertions, replacements or deletions. The transaction checks privacy invariants, the owner and the expected revision, applies the change, and records its receipt. Water updates maintain both the document and the per-entry feed under the same lock. Delegated writes use the same validated business operation under a directional family grant. The PostgreSQL transition row drains active writes and freezes the target for reverse recovery. The original Worker independently fences HTTP, cron, object RPC and alarm work.

## Device journal at /journal/

React, React Router, React Hook Form, TanStack Query and Dexie implement the device application in apps/web. Routes load on demand and share locale, calendar and active owner context. The local journal separates guest, restored and account namespaces. A revision check protects edits to structured care plans. Incremental sync commits a queued operation and local row together. A pulled competing edit goes into a separate conflicts store. Choosing a newer server value or resubmitting the local value clears that conflict transactionally. Reports query a date range in the compound owner/day index. Personal care plans have local persistence and encrypted backups. The journal exchanges changes through the per-entry water feed. The canonical product uses the care document API when the PostgreSQL writer is active.

Portable domain rules for doses, routines, appointments, sleep, and cycle reuse the legacy application's pure scheduling and validation functions. The Hono API uses the same PostgreSQL transactions and credential proof in its two adapters. Node crypto compatibility is required by the Worker adapter and the password KDF. S3 signing and R2 bindings implement the same object interface. Storage upload remains pending until a content digest check succeeds. Family water totals require current membership and a directional grant.

Verification codes have bounded attempts and expiry. PostgreSQL commits the challenge and encrypted mail job together. A Node interval or Worker cron leases jobs to a mail adapter. Mailpit provides local delivery. Hosted deliveries use the configured provider. Docker runs PostgreSQL, the Node service, S3, a mail sink and Caddy. Static Worker hosting uses the same app build.

To add a feature, put pure rules in packages/domain, validated API inputs in packages/contracts, durable data handling in a migration and service, and views under apps/web/src/features. Include a workflow test for retries, ownership or offline changes when those behaviors apply.


The portable operations service stores support tickets, rollout settings, counters and audit rows in PostgreSQL. Both runtimes share campaign rules and the original HTTP range semantics. PostgreSQL holds campaign metadata and media chunks under a transaction lock. The reminder scheduler shares the native state machine, locks each due device and checks its linked care revision before composing or sending. The source writer fence and the PostgreSQL freeze remain separate.

A valid legacy cookie can authenticate to the candidate when its signed owner and live digest match the imported ledger. Sign-out and password reset revoke both ledgers where applicable. Reverse recovery checks the original credential and session baseline before applying registered accounts, new proofs and revocations. It preserves the frozen target for mutations outside the verified mapping.

## Portable PostgreSQL installations

Node and Workerd call `createRuntime` in `apps/api/src/runtime.ts`, which composes the same handlers, policy services and job runner. Node owns the HTTP listener, connection lifecycle and timer. The portable Worker owns asset delivery, Hyperdrive and R2 bindings, request lifetime and cron dispatch. The portable mode uses no dedicated Cloudflare persistence for users beyond the replaceable R2 adapter. Workbox routes static requests within the existing service-worker scopes and cache lifecycle. API requests bypass these caches.

Migration 020 introduces a PostgreSQL installation state independent of the legacy writer transition. The database guard holds a shared lock for writes and coordinated external side effects. A migration can drain that lock, restore the frozen database into a separate target, verify it and explicitly select one destination. The original Durable Object recovery mechanisms remain in place. This work does not change the default compatibility preview or certify a legacy production cutover.
